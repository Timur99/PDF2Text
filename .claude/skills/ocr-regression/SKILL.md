# ocr-regression — измерение качества OCR

Правило проекта: **решения о движках и маршрутизации принимаются по цифрам.** Если цифр нет,
сначала цифры. Этот скилл — про то, как их получить воспроизводимо.

## 0. Сравнение движков с эталоном — `compare_engines.py`

```bash
.venv/bin/python compare_engines.py
```

Отвечает на вопрос «какой движок точнее», не требуя вручную вычитанного корпуса.

**Откуда берётся эталон.** У текстового PDF внутри уже лежит правильный текст: рендерим
страницу в картинку, распознаём, сравниваем с ним. Плюс три сгенерированные русские
страницы, где эталон — ровно то, что нарисовали (в `inputs/` чистой русской страницы нет:
у одного файла сломана кодировка, у другого слайды-картинки).

**Две метрики, потому что одной мало.** CER чувствителен к порядку обхода страницы и на
многоколоночных завышен у всех — сравнивать движки между собой, не с нулём. F1 по
мультимножеству слов от порядка не зависит и показывает чистое качество распознавания.

**Искусственные искажения** (наклон, размытие, JPEG-шум) — грубая замена сканам, которых
нет. Доказывают устойчивость модели, но **не** заменяют настоящие фото.

**Минимум пять страниц на условие.** Проверено больно: на двух страницах вывод получился
обратным тому, что дали девять.

## 1. Что уже есть и чего не хватает

`run_ocr_benchmark.py` (в корне) прогоняет `inputs/` через PaddleOCR, MinerU и Unlimited OCR,
складывает результат в `benchmark_outputs/<файл>/<движок>/` и пишет
`benchmark_outputs/benchmark_report.json`.

Что он меряет: время на файл и на страницу, число символов, peak VRAM (только CUDA), ошибки.

**Чего он НЕ меряет** — это и есть работа:

- CER/WER относительно эталона (ground truth нет вообще);
- статистику triage: тип PDF, доля страниц, ушедших в OCR, время pdf-inspector;
- native vs OCR на одном и том же файле;
- peak RAM на CPU (важнее VRAM: целевая машина — 18 GB без GPU).

## 2. Корпус

Живёт в `inputs/` (в `.gitignore` — документы не коммитим). Целевой состав: 20–30 файлов.

Обязательные категории, без них замер не считается представительным:

| Категория | Зачем | Сейчас |
| --- | --- | --- |
| Текстовый PDF (RU, EN) | native path, «дешёвый» сценарий | есть, 4 шт |
| Mixed PDF (текст + вставленные сканы) | главный сценарий hybrid | нет |
| Скан целиком | путь `scanned` | **нет** |
| Фото с телефона (перекос, тень) | целевой пользователь №1 | **нет** |
| Таблицы, многоколоночный layout | reading order, аргумент за MinerU | нет |
| Длинный документ (50+ страниц) | скорость, память, связность | нет |
| PDF со сломанной кодировкой шрифтов | ловушка: inspector зовёт его text_based | нет |

Эталоны — в `inputs/_truth/<имя файла>.txt`, UTF-8, только для 3–5 файлов: этого хватает для
CER/WER, а вычитывать эталон вручную дорого. Правила эталона: реальный порядок чтения,
переносы строк только там, где абзац, без служебных пометок.

## 3. Метрики

**CER** — расстояние Левенштейна по символам / длина эталона. **WER** — то же по словам.
Считать после нормализации: схлопнуть пробелы, привести к NFC, убрать переносы в конце строк.
Не приводи к нижнему регистру — регистр это часть качества.

Ориентиры: CER < 0.05 — хорошо для скана; > 0.15 — движок непригоден для этого класса
документов. Для кириллицы смотри отдельно: путаница `с/c`, `о/o`, `е/e` — классическая беда.

**Статистика triage** (важнее CER для нашего продукта):

- доля PDF, полностью закрытых native без единой страницы OCR — чем выше, тем лучше;
- доля страниц, ушедших в OCR, при неизменном качестве — чем ниже, тем лучше;
- ложные `text_based`: inspector сказал «текст», а native-выдача пустая или мусорная.
  Это самый дорогой класс ошибок — пользователь получает пустой результат вместо OCR.

## 4. Как прогонять

```bash
.venv/bin/python run_ocr_benchmark.py
```

Прогон долгий. Ограничители, которые уже прибиты в коде и которые **нельзя снимать не подумав**:

- `PP-OCRv5_mobile_det` вместо `server_det` — server-модель на M3 Pro 18 GB съела ~30 GB
  и ушла в своп (`run_ocr_benchmark.py:281`);
- длинная сторона рендера ≤ 1400 px (`run_ocr_benchmark.py:99`);
- `MAX_PAGES` — ставь 5–10 при отладке самого скрипта, `None` для настоящего замера;
- файлы сортируются по размеру, сначала мелкие — первые цифры приходят быстро.

MinerU запускается только если в PATH есть `mineru`, Unlimited OCR молча скипается без CUDA —
на Mac он всегда `skipped`, это ожидаемо, а не поломка.

## 5. Как сравнивать

Сравнение имеет смысл только при фиксированных: версии движка и модели, DPI рендера,
языке, железе. Всё это пиши в отчёт рядом с числами — через месяц не вспомнишь.

Сравнивай **на одинаковом входе**: если Paddle получил PNG 1400 px, а MinerU — исходный PDF,
разница в качестве может быть целиком про рендер, а не про движок.

Регрессия = ухудшение CER больше чем на 0.02 или рост доли OCR-страниц на том же корпусе.
Обнаружил регрессию — сначала воспроизведи на одном файле, потом ищи причину.

## 6. Что делать с результатом

1. Отчёт — в `benchmark_outputs/benchmark_report.json` (в `.gitignore`).
2. Выводы и принятые по ним решения — в `docs/DECISIONS.md`: дата, конфигурация,
   числа, вывод. Числа без вывода бесполезны, вывод без чисел — мнение.
3. Если замер меняет маршрутизацию — правь `backend/domain/routing.py` и дописывай тест
   в `tests/test_routing.py`. Это чистые функции, тестируются без движков и без файлов.
4. Файлы корпуса и эталоны не коммитим никогда: `inputs/` и `benchmark_outputs/` в `.gitignore`.
