## Видение

Приватный локальный инструмент для преобразования документов и фотографий
в редактируемый текст или структурированный Markdown без отправки данных в облако.
Для PDF сначала triage и native extraction; OCR — только для проблемных страниц.

## Целевая аудитория

1. Пользователь без GPU: распознаёт фотографии и сканы на CPU. **Главный.**
2. Пользователь документов: быстро вытаскивает текст из text-based PDF и
   конвертирует сложные PDF/Office в Markdown.
3. Продвинутый пользователь с GPU: обрабатывает длинные и сложные документы.
   Не приоритет: у нас нет ни машины для разработки под него, ни способа
   доставить это в DMG.

## Основные сценарии

- Загрузить файл, увидеть прогресс, скопировать или скачать результат.
- Для PDF видеть: native / OCR / hybrid и какие страницы пошли в OCR.
- Сопоставить исходную страницу и распознанные блоки.
- Выбрать `Авто`, `Быстро`, `Структурно` или `Длинный документ`.
- Повторить задачу с другим движком и сравнить результаты.
- Удалить исходник и все результаты с устройства.

## Метрики продукта

- Доля PDF, полностью закрытых native path без OCR.
- Доля страниц, отправленных в OCR (ниже — лучше при том же качестве).
- Доля успешно завершённых задач.
- Время до первого результата и страниц в минуту.
- CER/WER на тестовом корпусе RU/EN.
- Точность таблиц и reading order для структурных документов.
- Peak RAM/VRAM и размер установки.
- Доля задач, которые пользователь перезапускает другим движком.

Ни одна из этих метрик сейчас не собирается автоматически. Инструмент — этап 0.

Два изменения относительно первой редакции плана, оба намеренные:

**DMG поднят с шестого места на третье.** Упаковка вскрывает размер сборки (только
paddlepaddle+paddleocr+paddlex — сотни мегабайт), скачивание моделей при первом запуске,
подпись и нотаризацию. Ловить это после того, как прикручен второй ML-стек, вдвое дороже.
Сначала выпускаем DMG, который умеет triage + PaddleOCR, дальше движки — инкремент
к работающему продукту, а не условие его появления.

**Unlimited OCR отложен из нумерованных этапов.** Требует NVIDIA и 12+ GB VRAM. Машина
разработки — M3 Pro 18 GB без CUDA: этап невозможно ни собрать, ни протестировать,
и в macOS DMG он не попадает. Возвращаем к обсуждению, только если этап 0 покажет,
что постраничный PaddleOCR реально рвёт связность длинных документов — и тогда как
опциональный серверный профиль, а не как режим приложения.

## Этап 0 — корпус и метрики

**Цель:** получить цифры, на которых можно принимать решения о движках и маршрутизации.

**Почему не закрыт.** В `inputs/` четыре текстовых PDF: ни одного скана, ни одного фото,
ни одного файла с таблицами или сломанной кодировкой. `run_ocr_benchmark.py` меряет время
и число символов, но не считает ни CER/WER, ни статистику triage, ни peak RAM. Последний
прогон не доехал до отчёта. То есть главное утверждение продукта — «triage корректно делит
text/scanned/mixed» — не проверено на классах документов, ради которых он существует.

- Собрать корпус 20–30 файлов по категориям из скилла `ocr-regression`.
- Ground truth для 3–5 файлов в `inputs/_truth/`.
- Дописать в `run_ocr_benchmark.py`: CER/WER, статистику triage, peak RSS.
- Зафиксировать версии моделей и минимальные требования.

**Готово, когда:** есть отчёт с CER/WER и долей OCR-страниц по каждой категории документов,
и по нему принято записанное решение о параметрах маршрутизации.

## Этап 1 — вертикальный MVP: triage + PaddleOCR (сделан)

Работает: FastAPI, upload, triage через pdf-inspector, native path без OCR для text-based PDF,
PaddleOCR для страниц, которым он нужен, drag-and-drop UI с прогрессом и меткой
native/OCR/hybrid, экспорт TXT/Markdown/JSON, удаление задачи, лимиты и безопасные имена.

Отклонения от исходного плана — приняты сознательно, но должны быть зафиксированы:

- фронтенд ванильный JS, а не React+Vite;
- jobs в памяти, а не SQLAlchemy/SQLite;
- `BackgroundTasks` и поллинг, а не очередь и WebSocket.

## Этап 1.5 — стабилизация (текущий)

**Цель:** приложением можно пользоваться каждый день и доверять его выдаче.

Полная спека с критериями готовности — `SPEC-stage-1.5.md`. Кратко:

- S1. Результат не врёт о своей полноте: `ocr_reason`, `skipped_pages`, баннер в UI.
- S2. Задачи переживают рестарт: восстановление из `data/jobs/*/job.json`.
- S3. Retention: TTL 72 часа, очистка промежуточных PNG после падения.
- S4. Очередь на одного воркера и рабочая отмена.
- S5. Проверка типа файла по содержимому, потоковое чтение аплоада.
- S6. Логи без содержимого документов; ошибки пользователю без внутренних путей.

**Готово, когда:** приложение неделю живёт запущенным, переживает перезапуски, чистит себя
само, длинная задача отменяется, а неполный результат сообщает об этом на экране.

## Этап 2 — качество и удобство

- Просмотр страниц с bounding boxes (для OCR-страниц).
- Редактор результата и копирование по страницам.
- Пакетная загрузка, отмена, повторный запуск.
- Предобработка изображений: rotation, deskew, contrast, denoise.
- История локальных задач и поиск.
- Regression fixtures: native PDF, mixed PDF, scan, photo.
- Benchmark CLI: triage stats + OCR metrics.

**Развилка: React.** Ванильный JS дожил до этой точки нормально, но bbox-оверлей и
постраничный редактор — ровно то место, где рукописный DOM начинает болеть. Решение
принимать **до** начала этапа, не в середине.

**Готово, когда:** типовые ошибки видимы, воспроизводимы и не требуют терминала.

## Этап 3 — упаковка и DMG

- Desktop-оболочка Tauri над тем же UI/API.
- Первый unsigned `.dmg`, затем подписанный и нотаризованный.
- Стратегия моделей: что кладём в бандл, что скачиваем при первом запуске
  с подтверждением и понятной оценкой диска.
- Диагностика и export support bundle без документов.
- Docker Compose с профилями — для тех, кто ставит не на Mac.

**Готово, когда:** человек скачивает DMG, перетаскивает в Applications, открывает и
обрабатывает скан, ни разу не открыв терминал.

## Этап 4 — MinerU как структурный режим

- Отдельный MinerU service/CLI adapter, изолированное окружение.
- Markdown preview, JSON и ZIP артефактов.
- Таблицы, формулы, изображения и reading order.
- CPU `pipeline`; `hybrid/vlm` — только при доступном GPU.
- Health/capability checks и мастер установки моделей.

**Готово, когда:** сложный PDF/Office файл преобразуется в Markdown, а отсутствие
MinerU не мешает дефолтному path (inspector + PaddleOCR).

## Этап 5 — auto-routing и сравнение

Требует закрытого этапа 0: без цифр это гадание.

- Рекомендация движка по triage + формату + длине + layout + железу.
- Side-by-side сравнение native vs OCR / двух OCR-backend'ов.
- Confidence/warnings и объяснение маршрутизации.

**Готово, когда:** auto-routing выигрывает у «OCR всего» на корпусе и никогда
не переключает backend незаметно.

## Отложено — Unlimited OCR

Опциональный GPU-профиль вне DMG. Условия возврата к теме: закрытый этап 0 показал
проблему связности на длинных документах, и появилась машина с NVIDIA для разработки.
Не использовать для TextBased PDF ни при каких условиях без явного выбора пользователя.

## Стек

Как есть сейчас:

- Backend: Python 3.12, FastAPI, Pydantic. Jobs — JSON на диске.
- Triage: pdf-inspector 1.14 (Python bindings).
- OCR: PaddleOCR 3.7 / paddlepaddle 3.3, модель `PP-OCRv5_mobile_det`, рендер pymupdf.
- Frontend: ванильный JS/HTML/CSS, поллинг статуса.
- Tests: pytest.

Куда идём:

- Очередь: `asyncio.Queue` + один воркер (этап 1.5). Dramatiq/Redis — только если появится
  многопользовательский сценарий, чего в планах нет.
- SQLite — когда понадобятся история и поиск (этап 2).
- React + TypeScript + Vite — решение перед этапом 2.
- Tauri — этап 3.
- Логи: stdlib logging (этап 1.5); structlog — если формата перестанет хватать.

## Риски

- **Ложный `text_based`** на PDF со сломанной кодировкой шрифтов: пользователь получает
  пустой или мусорный результат вместо OCR. Самый дорогой класс ошибок, нужен fallback
  по warnings/confidence и отдельная категория в корпусе.
- **Размер сборки.** Три ML-стека в одном DMG нереальны; MinerU обязан быть изолирован,
  часть моделей — докачиваться. Проверять на этапе 3, а не на шестом.
- **Память на 18 GB.** Уже обжигались: `server_det` съел ~30 GB и ушёл в своп. Все параметры
  рендера и моделей подобраны под это ограничение, менять их — только с замером.
- Конфликтующие CUDA/PyTorch зависимости: изолировать движки сервисами.
- OCR-галлюцинации VLM: хранить warnings и давать сравнение с исходником.
- Кириллица и смешанные языки: собственный RU/EN regression corpus.
- Лицензии моделей: license manifest для каждой сборки.
- Нестабильные API молодых моделей: адаптеры и version pinning.
- **Документы проекта вне git.** `.local-dev/` и `.cursor/` в `.gitignore`: план, архитектура
  и решения существуют в одном экземпляре на одном диске. Перенести `docs/` в репозиторий.
